The Problem

Why raw LLMs fail in regulated workflows

Most AI chatbots in finance are built on raw LLM loops. The model decides what to do next, which means it can hallucinate, loop, or skip a legally required step.

Infinite loops

Without hard exit conditions, LLM agents repeat questions, re-enter stages, and consume quota indefinitely.

Non-deterministic decisions

A loan approval is a legal commitment. LLMs with temperature above zero can approve the same application differently on different runs.

Stage skipping

LLMs can be persuaded to skip KYC or jump to approval. In regulated lending, skipping a mandatory step is a compliance violation.

Quota exhaustion

Without call limits, a single stuck conversation can burn thousands of tokens unpredictably in production.

The Solution

A finite-state machine that LLMs obey

POLARIS wraps every agent call inside a 9-state FSM. The machine decides transitions, the LLM only generates language within a bounded stage.

Second Workflow

Factoring back office: payment matching, collections, portfolio monitor

Same FSM engine, a different regulated workflow. Incoming bank payments never get matched by an LLM guess, a wrong automatic match moves real money to the wrong ledger. Three sections run on shared ledger state: Payment Matching, Collections, and Portfolio Monitor.

ConfidenceTierCriteria
100AUTO_APPLYExact reference and exact amount. Applied, no review.
90AUTO_APPLY_LOGGEDUnambiguous amount match, no clean reference. Applied with an audit-log entry.
70-89REVIEWProbable match: short-pay, combined remittance, or partial payment. Suggested, waits for a human.
<70EXCEPTIONAmbiguous or no signal. Routed to the exception queue, never guessed.

These are POLARIS's own tier criteria, not a published vendor scale. The demo bank feed is deliberately messy: wire-fee short-pays, one wire covering three invoices, a reused PO reference matching two invoices, and unreferenced payments with colliding amounts, so the tier engine has real work to do.

The review and exception queues are actionable: each row shows the candidate invoice(s) and confidence, and a human can approve (applies the match to the ledger) or send to exceptions. Auto-applied tiers and human approvals both call the same underlying function, so ledger state is identical regardless of who approved the match. A payment can never be applied twice. Every decision across all four tiers plus human actions lands in a confidence-scored audit trail: timestamp, actor, payment id, matched invoice ids, tier, confidence, and reason, searchable in the UI.

Collections: a guarded FSM per invoice

Past-due invoices are ranked by priority (factored amount × aging-bucket weight × dispute history) and each case runs its own state machine, not a freeform chat loop. Outreach follows a deterministic dunning ladder by channel: first touch WhatsApp, second email, third and beyond escalates to a phone-call task. The LLM only drafts message wording; who to contact, when, and what happens next is deterministic.

Portfolio monitor

Computed from the same invoice and debtor ledger, no separate data store: open AR total and funds employed, concentration by account debtor against a configurable warning band, aging bucket distribution with percent over 60 days flagged, dilution rate (short-pays plus disputes as a percent of face value processed), and collection rate. Presented as a covenant-style table: metric, current, threshold, status. An export data tape button produces a real invoice-level CSV of the sample ledger.

Code Quality

Anti-loop safeguards: 3 independent layers

state.py · ConversationState
# Layer 1: Terminal state lock, once ended, always ended
def is_terminal(self) -> bool:
    return self.terminal_state is not None

# Layer 2: Max call quota (6 calls per session max)
if self.state.total_agent_calls >= MAX_AGENT_CALLS:
    self.state.terminal_state = TerminalState.CUSTOMER_DROPPED
    return "Maximum agent calls exceeded. Conversation ended."

# Layer 3: Duplicate call blocking via input hash
def can_call_agent(self, agent_name: str, input_hash: str) -> bool:
    call_signature = f"{agent_name}:{input_hash}"
    if call_signature in self.agent_call_history:
        return False  # Same agent + same inputs = blocked forever
    return True
underwriting_agent.py · 4 Deterministic Rules
# Rule 1: Credit score gate (fetched live from Credit Bureau)
if credit_score < 700:
    return {"decision": "REJECTED", "reason": f"Score {credit_score}/900 below minimum"}

# Rule 2: Instant approval within preapproved limit
if requested_amount <= preapproved_limit:
    return {"decision": "APPROVED", "emi": calculate_emi(amount, rate, tenure)}

# Rule 3: Salary slip required (1x to 2x limit zone)
if requested_amount <= preapproved_limit * 2:
    if salary and calculate_emi(amount, rate, tenure) <= salary * 0.5:
        return {"decision": "APPROVED"}
    return {"decision": "NEED_SALARY_SLIP"}

# Rule 4: Hard reject above 2x limit, no exceptions
return {"decision": "REJECTED", "reason": "Exceeds 2x eligible limit"}
Underwriting Engine

4 rules. Pure code. No LLM.

The most critical decision in a loan, approve or reject, is never left to an LLM. Every rule is deterministic, explainable, and auditable.

1
Credit Score Gate
Reject immediately if credit score is below 700/900. Checked against the live credit bureau API, not a cached score.
2
Instant Approval
Approve if requested amount is at or below the preapproved limit. EMI calculated with the reducing balance method.
3
Income Verification
If amount is at or below 2x limit, require a salary slip. Approve only if EMI is at or below 50% of verified monthly salary.
4
Hard Limit Reject
Reject unconditionally if amount exceeds 2x the preapproved limit. No exceptions, no negotiations.
One Paragraph Pitch

The architecture pattern for regulated AI

POLARIS is a multi-agent system built to demonstrate a production architecture pattern that most AI companies are still struggling to implement: deterministic FSM governance over LLM agents, applied to two regulated financial workflows on the same engine. Loan origination runs a Master Agent through a 9-state finite-state machine with three independent anti-loop mechanisms, applying four underwriting rules with zero LLM involvement. Factoring back office runs payment matching through four confidence tiers, auto-apply, auto-apply-with-audit-log, human review, or exception queue, so a low-confidence match never gets guessed, plus collections through a guarded per-invoice FSM where the same dunning message can never be sent twice, and a portfolio monitor computed straight from ledger state. Neither workflow can hallucinate a decision, skip a mandatory step, or loop, a pattern that translates directly to any regulated AI workflow.
