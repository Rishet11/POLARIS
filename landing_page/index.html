The Problem

Why raw LLMs fail in regulated workflows

Most AI chatbots in finance are built on raw LLM loops. The model decides what to do next — which means it can hallucinate, loop, or skip legally required steps.

🔄

Infinite Loops

Without hard exit conditions, LLM agents repeat questions, re-enter stages, and consume quota indefinitely.

🎲

Non-Deterministic Decisions

A loan approval is a legal commitment. LLMs with temperature > 0 can approve the same application differently on different runs.

⚠️

Stage Skipping

LLMs can be persuaded to skip KYC or jump to approval. In regulated lending, skipping a mandatory step is a compliance violation.

💸

Quota Exhaustion

Without call limits, a single stuck conversation can burn thousands of tokens unpredictably in production.

The Solution

A finite-state machine that LLMs obey

POLARIS wraps every agent call inside a 9-state FSM. The machine decides transitions — the LLM only generates language within a bounded stage.

Code Quality

Anti-loop safeguards: 3 independent layers

state.py · ConversationState
# Layer 1: Terminal state lock — once ended, always ended
def is_terminal(self) -> bool:
    return self.terminal_state is not None

# Layer 2: Max call quota (6 calls per session max)
if self.state.total_agent_calls >= MAX_AGENT_CALLS:
    self.state.terminal_state = TerminalState.CUSTOMER_DROPPED
    return "Maximum agent calls exceeded. Conversation ended."

# Layer 3: Duplicate call blocking via input hash
def can_call_agent(self, agent_name: str, input_hash: str) -> bool:
    call_signature = f"{agent_name}:{input_hash}"
    if call_signature in self.agent_call_history:
        return False  # Same agent + same inputs = blocked forever
    return True

# Rule 1: Credit score gate (fetched live from Credit Bureau)
if credit_score < 700:
    return {"decision": "REJECTED", "reason": f"Score {credit_score}/900 below minimum"}

# Rule 2: Instant approval within preapproved limit
if requested_amount <= preapproved_limit:
    return {"decision": "APPROVED", "emi": calculate_emi(amount, rate, tenure)}

# Rule 3: Salary slip required (1x to 2x limit zone)
if requested_amount <= preapproved_limit * 2:
    if salary and calculate_emi(amount, rate, tenure) <= salary * 0.5:
        return {"decision": "APPROVED"}
    return {"decision": "NEED_SALARY_SLIP"}

# Rule 4: Hard reject above 2x limit — no exceptions
return {"decision": "REJECTED", "reason": "Exceeds 2x eligible limit"}
Underwriting Engine

4 rules. Pure code. No LLM.

The most critical decision in a loan — approve or reject — is never left to an LLM. Every rule is deterministic, explainable, and auditable.

1
Credit Score Gate
Reject immediately if credit score < 700/900. Checked against live Credit Bureau API, not cached score.
2
Instant Approval
Approve if requested amount ≤ preapproved limit. EMI calculated with reducing balance method.
3
Income Verification
If amount ≤ 2× limit, require salary slip. Approve only if EMI ≤ 50% of verified monthly salary.
4
Hard Limit Reject
Reject unconditionally if amount exceeds 2× preapproved limit. No exceptions, no negotiations.
One Paragraph Pitch

The architecture pattern for regulated AI

POLARIS is a multi-agent loan sales system built to demonstrate a production architecture pattern that most AI companies are still struggling to implement: deterministic FSM governance over LLM agents. A Master Agent orchestrates four specialized Worker Agents through a 9-state finite-state machine with three independent anti-loop mechanisms. The underwriting engine applies four hard rules with zero LLM involvement, calculates EMIs using the reducing balance method, and generates a formal PDF sanction letter on approval. The mock API layer simulates CRM, credit bureau, and offer mart endpoints with 10 test customers spanning approved, rejected, KYC-failed, and low-credit scenarios. The full conversation cannot hallucinate an approval, cannot skip KYC, and cannot loop — a pattern that translates directly to any regulated AI workflow.
